driftwatch Phase 1 benchmark baseline
=====================================

Machine: AMD Ryzen 7 6800HS, windows/amd64, go1.26.4
Captured: 2026-07-31

Each package is benchmarked in its own process. The 1M-key oracle
benchmarks are sensitive to leftover garbage from seeding, so they call
runtime.GC() before resetting the timer; without it the first iterations
run two to three times slower than the steady state and the reported
average depends on how many iterations the framework chose.

The memory result is 25% over budget and is recorded as docs/KNOWN_GAPS.md
G-001, with the remaining cost accounted for and the fix scoped. It started
Phase 1 at 5.2 GiB: the history ring was preallocating sixteen ~300-byte slots
for every key including the majority that have seen a single event, and cloning
a map into the ring on every apply. Growing the ring lazily and storing the
resulting value by reference brought it to 640 MiB and took BenchmarkOracleApply
from 345ns with 2 allocations to 186ns with none.

Notes on reading these
----------------------

BenchmarkProjectionApply and BenchmarkOracleApply both allocate on the set path
because a member set is cloned per fold; the projection contract requires the
previous value not to be modified, and the oracle stores what it is handed.

BenchmarkSeqTrackObserveWithGaps is the unhealthy path, where every event
reveals a hole and the gap set is permanently at its interval cap. At 1.3us it
is roughly 45x the steady-state cost, which is the price of the cap enforcement
scan. It is bounded and it only happens while events are being lost.

BenchmarkProjectionApplyTemplated is the cost of a non-identity key template:
text/template execution, about 3.4x the identity path. The identity template is
the default and is answered by returning the field directly.
